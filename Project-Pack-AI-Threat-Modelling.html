Project pack · 1 of 5 · Project brief

Threat-modelling my three public AI demos

Owner: Shivam Kumar · Delivered 20 Oct 2026 · Status: complete, with open items (see RAID log)
How this pack was made: it is a retrospective, reconstructed after delivery from my evidence log, report files and Git commit history. The dates are real. I did not set time estimates at the start, so there is no "planned versus actual" for effort, and I say so in the review.

Goal

Find, fix and openly report the security and privacy weaknesses in my three live AI demos (a GDPR request classifier, a RAG chatbot and a radiology summariser), seen from the builder's point of view, so that the documents match what the code really does.

In scope

  • Data-flow diagram, trust boundaries and STRIDE review for each app
  • Light testing of my own live apps, with made-up data only (single requests, no flooding)
  • Rating each finding Low/Medium/High, with evidence and a fix status
  • Fixing what I could, then retesting on the live apps
  • Publishing the three reports (CC BY 4.0) and a plain-English article

Out of scope

  • A penetration test, flood or load testing, or testing anything I do not own
  • Making the radiology model accurate (documented, not fixed) and any clinical or legal review
  • Making the demos production-grade or paying for hosting

Critical path

Test, then reports, then fixes, then live retest, then publish. The reports had to be written before the fixes (they set the priorities), and publishing had to wait for the retest so that every status in the reports was true.

Change during delivery

Milestone 4 grew. The Fly.io deploy was blocked by a billing request, so I rebuilt the radiology demo as a free Streamlit app (see issue I1 in the RAID log). This added work but removed several risks by design (no public API, no deploy token).

Project review: what I learned

Completed 20 Oct 2026. Reviewed 27 Oct 2026.

Result against the brief

BriefDelivered
3 apps threat-modelled3 reports, 22 findings, each rated with a fix status
Fix and retest liveGDPR and radiology fixed and retested; RAG hardened, except the dependency pins (reverted)
Publish with limits statedGitHub repo and Medium article; open findings listed

What went well

  • Writing the reports first set clear priorities for the fixes.
  • Retesting on the live apps caught two things my laptop did not: a stale classifier and a failing build.
  • Recording open items in public kept the claims honest.

What did not go to plan

  • I pushed pinned dependencies without testing them on a matching environment, which took the RAG demo down briefly.
  • I built the radiology deploy around a host without checking it needed payment details, which forced a rebuild.
  • I did not set effort estimates or a written definition of done at the start, so I cannot compare the plan with the actual time taken.

Lessons and what I would change

#Next time
1Write time estimates and a done-checklist in the plan before starting, and compare them at the end.
2Test dependency and infrastructure changes on a copy that matches the host before pushing.
3Check a host's billing and limits before designing around it.
4Treat the live system as the test: retest after every push.

Follow-on work

A prompt-injection test set for the chatbot, a dependency lock file, per-IP limits and clinician scoring of the radiology output. Next project: use this pack's templates from day one, with estimates set in advance.
